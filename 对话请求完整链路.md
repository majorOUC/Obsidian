# 对话请求完整链路

> 智能客服 Agent（Python 侧）处理一次 `POST /api/chat` 的全过程。
> 所有位置均为实测代码，格式 `文件:行号`。最后更新：2026-09-04。

---

## 一、主干流程

```
POST /api/chat
  │
  ├─① 入口：取 memory_id / message / authorization
  │
  ├─② 装载上下文：事实区 + 历史摘要 + 最近对话；解析 user_id
  │
  └─③ 会话锁内，看有没有待确认操作：
        ├─ 用户回"确认" → 恢复图，执行敏感操作（0 次 LLM 推理）
        ├─ 用户回"取消" → 结束图，回"已取消"
        └─ 其他         → 正常跑图
                              │
   ┌──────────────────────────┘
   ▼
 LangGraph:  guardrail → orchestrator → [confirm ⇄ interrupt] → execute_sensitive
                              │
   ┌──────────────────────────┘
   ▼
④ Router 里流式调 Summary LLM，边出字边过 Holdback 正则检查 → SSE 推给前端
⑤ 收尾：存助手回复、异步提画像、异步压缩历史
```

## 二、逐步说明

### ① 入口

| 步骤     | 位置                                                 | 做什么                                                                                        |
| -------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 路由     | `app/routers/chat.py:41`                           | 取`memory_id` / `message` / `authorization`                                             |

### ② 装载上下文（并行）

`chat.py:119` `asyncio.gather(get_conversation_context(), get_user_id())`

`get_conversation_context()`（`app/services/conversation.py:147`）返回三段，顺序即优先级：

```
【已确认事实】  ← Redis Hash facts:{memory_id}，业务操作结果原文，永不压缩
【历史摘要】    ← LLM 压缩产物，有损
【最近对话】    ← history[-8:] 原文
```

然后：`chat.py:129` 存用户消息 → `chat.py:132` `set_current_user_id()` 写 ContextVar（工具层靠它认人）。

### ③ 会话锁与 pending 分流

```python
async with _session_lock(memory_id):                    # chat.py:161
    snapshot = await graph.aget_state(config)           # chat.py:162  config.thread_id = memory_id
    pending_exists = bool(snapshot and snapshot.next)   # 图停在 confirm 就说明有 pending
```

| 用户消息                | 动作                                                                        | LLM      |
| ----------------------- | --------------------------------------------------------------------------- | -------- |
| 命中`CONFIRM_PATTERN` | `graph.ainvoke(Command(resume=True))`，只重放 confirm + execute_sensitive | 0 次推理 |
| 命中`CANCEL_PATTERN`  | `Command(resume=False)`，图结束，Router 回"已取消"                        | 0        |
| 其他                    | 先`Command(resume=False)` 隐式取消 pending，再正常跑图                    | 正常     |

两个正则是**整句短句白名单**（`chat.py:22-23`），防止"确认下订单状态"被误判成确认购买。

## 三、图内部

拓扑（`app/graph/builder.py:207-252`）：

```
guardrail ──should_continue──> orchestrator ──有 pending_action──> confirm ──确认──> execute_sensitive
    │                              │                                 │
    END                            END                               END（取消）
```

### guardrail_node（`builder.py:35`）

除了安检，还兼任**每轮状态重置**：`task_results / summary_context / pending_action / user_confirmed` 全置 `None`（`:47-52`）。因为 checkpointer 下 state 跨请求持久，不清会把上一轮结果带到本轮，导致重复回复。

安检三层递进，越靠前越便宜（`app/guardrails/checker.py:89`）；层内还有两个短路：空消息直接放行（`keyword_checker.py:144`）、关键词库加载不可用则跳过本层送下层（`:151`）：

| 层级            | 位置                       | 判定                                                                                                        |
| --------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 1 黑名单        | `keyword_checker.py:134` | AC 自动机 <1ms，子串命中即拒；未命中返回 None 进下一层                                                    |
| 2 向量检测层    | `vector_layer.py`        | 语义变体相似度，score≥0.90 直接拒；基础设施不可用自动跳过；**低分和中间带全部进 LLM**（09-08 移除低分放行） |
| 3 Guardrail LLM | `checker.py:40`          | 越狱 + 相关性双判断（qwen-turbo，带上一轮对话做上下文感知），越狱或不相关则拒；**仅拦截落 guardrail_log（5 字段）** |

拒绝时固定回 `GUARDRAIL_REJECT_REPLY`，**真实原因只进日志**（`builder.py:74-81`）。

### orchestrator = `primary_agent`（`app/agents/primary.py:64`）

```
a. 注入 {current_date}/{weekday}/{conversation_context}          :78-84
b. Mem0 画像检索，注入 {user_memories}                            :99
c. emit step=planning                                            :115
d. 结构化输出 → TaskPlan（最多 3 次，失败 sleep(1) 退避）          :121
      CancelledError（客户端断开）→ 直接返回                      :124
      APIConnectionError → 快速失败，不叠加重试                   :132
e. plan.tasks 为空（闲聊/查画像）→ 不派任务，直接组 summary_context :152
f. emit step=executing                                           :172
g. executor.execute(plan, user_id)                               :177
h. 扫描 pending_action，只取第一个；其余改写为"请前一操作完成后重试"  :188-199
```

### TaskExecutor（`app/agents/executor.py:90`）

按 `depends_on` 拓扑分批，同批 `asyncio.gather` 并行：

- 前置任务失败 → 当前任务 `skipped=True` 短路（`:107-121`）
- 前置是 pending 标记 → **不把标记原文喂给下游 LLM**，改写成"需用户确认"（`:124-129`）
- 任务级熔断：复用工具层同名 `*_worker` 熔断器，OPEN 直接拦，不跑 LLM（`:36-41`、`:144`）
- `voucher` / `reservation` 调用时多传一个 `user_id`（`:166-169`）

### 子 Agent（以优惠券为例，`app/agents/voucher_agent.py`）

固定管线，代码里无循环：

```
LLM 1  意图判断 → VoucherIntent{action, shop_name, pay_value, actual_value}
  ├─ query_mine / query_shop → 执行查询工具，结果原文直返（不让子 Agent 复述）
  └─ purchase:
       工具 1  查该店优惠券
       短路    结果里没有 "[券ID:" → 直接返回，不进 LLM 2
       白名单  legal_ids = 正则抽 [券ID:(\d+)]
       LLM 2   bind_tools([purchase_voucher]) 选券
       校验    voucher_id 不在 legal_ids → 拒绝执行（封死幻觉 ID）
       工具 2  purchase_voucher → 敏感拦截，只返回确认标记
```

工具层外壳 `app/agents/retry.py`：`QUERY_TOOLS` 幂等可重试，`ACTION_TOOLS` **不重试**（`:30-46`、`:96`），错误分类交 `error_handler`。

### 敏感操作（`app/agents/sensitive.py`）

工具**不执行**，返回 `__PENDING_CONFIRMATION__{json}` 标记 → 冒泡到 `state.pending_action`。
确认文案带券名+售价+抵扣额，用户确认前就能发现买错券。

`confirm_node`（`builder.py:95`）调 `interrupt()` 暂停图，`ainvoke` 返回含 `__interrupt__` 的 dict。
Router 取出 question → 发 `message`（气泡）+ `confirm`（弹按钮）两个事件，**不走 Summary LLM**。

### execute_sensitive_node（`builder.py:114`，用户确认后）

```
:135  set_current_user_id()     ← 重放路径必须重设 ContextVar，否则工具认不到人
:146  result_text = 真实工具结果  ← 这个字符串此生只在这里出现一次
:150  ok=True 时写入 facts:{memory_id}（操作事实原样保留）
:158  用真实结果替换原 pending 条目（state 无 reducer，追加会残留标记文本）
:173  沿用第一轮 summary_context，只更新 results
```

> **确认后的重放不重新规划、不重跑子 Agent，零 LLM 推理成本。**

## 四、输出阶段（在 Router 里，不在图内）

```
chat.py:220  有 __interrupt__ → 发确认问题，结束
chat.py:228  guardrail_passed=False → 发固定拒绝语
chat.py:234  有 task_results + summary_context：
             prompt = load_prompt("summary_system.txt").format(**summary_context)
             流式调 Summary LLM
               ↓ Holdback 输出防护（chat.py:248-298）
                 HOLDBACK_SIZE = 50
                 buffer 满 50 → 检查前段（output_checker 三类正则：
                   system prompt 泄漏 / 内部技术信息 / PII）
                   命中 → 输出"[内容已安全过滤]"并中断
                   通过 → 输出安全部分，buffer 留最后 50
                 流结束后再检查剩余 buffer
chat.py:305  Summary LLM 未初始化 → 直接拼工具原文返回
chat.py:310  无 task_results → 从 messages 倒序找第一条助手文本
chat.py:333  任何异常 → 日志留 traceback，用户只看通用提示
```

**架构特点：图内只做规划和工具执行，最终回复生成在图外。** 好处是确认重放时不必重跑规划；代价是最终回复不进 checkpointer。

## 五、收尾（三个动作都不 await）

| 动作                                                                                                                          | 位置                |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| 存助手回复（**存的是复述稿，不是工具原文**）                                                                            | `chat.py:345`     |
| 异步提画像：`create_task(mem0.analyze_chat_history)`，按 `mem0_marker:{user_id}` 增量计数，每 N 轮才分析新增消息          | `chat.py:351`     |

响应形态：`StreamingResponse`，`text/event-stream`，头带 `no-cache` / `X-Accel-Buffering: no` / `keep-alive`（`chat.py:371`）。
事件类型只有三种：`step`（planning/executing）、`message`、`confirm`，最后 `done`。

## 六、LLM 调用预算

| 场景                       | 次数          | 组成                                                                                        |
| -------------------------- | ------------- | ------------------------------------------------------------------------------------------- |
| 任意消息基础成本           | **+1**  | Guardrail LLM（黑名单未命中的都进向量层→LLM，09-08 后无白名单/低分放行）                    |
| 纯问候                     | **3**   | Guardrail + Plan + Summary                                                                  |
| 查店铺                     | **4-5** | + shop 子 Agent                                                                             |
| 查优惠券                   | **5**   | + VoucherIntent                                                                             |
| **买券（两个请求）** | **7**   | 请求1：Guardrail + Plan + Intent + 选券 + Summary；请求2：Summary（确认重放本身 0 次推理） |

## 七、数据都在哪

| Redis Key                   | 内容                                                                               | TTL   |
| --------------------------- | ---------------------------------------------------------------------------------- | ----- |
| `{memory_id}`             | 消息历史 JSON 数组，`[{type, content, timestamp}]`，**全量保留供前端显示** | 1 天  |
| `summary:{memory_id}`     | `{"text": 摘要, "position": 已压缩到下标}`，同 key 同生共死                      | 1 天  |
| `facts:{memory_id}`       | 操作事实 Hash，field=`工具:单号`，value=`{tool,text,ts}` 原文                  | 1 天  |
| `compressing:{memory_id}` | 压缩分布式锁（`SET NX`）                                                         | 30 秒 |
| `mem0_marker:{user_id}`   | 画像增量分析计数                                                                   | —    |
| `mem0_reset:{user_id}`    | 画像清空时间戳，早于此的对话不再分析                                               | —    |
| `chat:user:{memory_id}`   | **只删不写**，`get_user_id` 已改为从 `memory_id` 直接提取                | —    |

Milvus：`hmdp_knowledge`（RAG 知识库）与 `mem0_user_preferences`（用户画像）两个 collection，schema 不同不可共用。
LangGraph 检查点：独立 Redis 8 实例（内置 RediSearch + RedisJSON），TTL 由 `CHECKPOINT_TTL_MINUTES` 控制。
